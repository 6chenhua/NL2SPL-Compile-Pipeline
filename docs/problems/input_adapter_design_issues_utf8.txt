NL2SPL InputAdapter 设计问题分析报告
结构化自然语言适配层的核心设计缺陷
1. 背景
NL2SPL 是一个自然语言到 SPL 的编译器，通过 12 个阶段的 Pipeline 完成编译。InputAdapter 层是 Pipeline 的入口，负责将任意形态的自然语言输入规范化为 CanonicalCompileInput 契约，供下游所有阶段消费。
当前设计中存在两个具体实现：
StructuralNLAdapter：处理结构化自然语言（有标题分节的文档）
GenericNLAdapter：作为兜底，处理自由文本输入
两者通过 InputAdapterRegistry 路由，按优先级顺序尝试匹配。
2. 当前实现概述
StructuralNLAdapter 的核心是一个固定标题映射表：
STRUCTURAL_NL_SECTIONS = {
    "task family": "task_family",
    "inputs for each run": "inputs_for_each_run",
    "required outputs": "required_outputs",
    "reusable process": "reusable_process",
    "policies": "policies",
    "failure handling": "failure_handling",
    "delegation policy": "delegation_policy",
}
加上 20+ 个硬编码变量别名（VARIABLE_NAME_ALIASES），adapt() 方法通过 if/elif 链将匹配到的标题映射到固定的处理逻辑，组装 HardFacts 和 CompileHints。
路由逻辑：Registry 按 StructuralNL → GenericNL 顺序尝试，第一个 detect() 返回 matched=True 的 adapter 胜出。GenericNLAdapter.detect() 无条件返回 True，作为 catch-all 兜底。
3. 核心问题分析
3.1 问题一："结构化"的定义过窄
当前 StructuralNLAdapter 不是一个通用的结构化文档检测器，而是一个针对特定文档模板的解析器。
判断一个文档是否"结构化"的标准应该是形态学（morphological）的，而非词汇学（lexical）的：
Markdown 标题层级（#, ##, ###）
键值对格式（YAML frontmatter、dl 标签）
列表结构（有序/无序列表）
表格和代码块
这些才是"结构化"的判定依据。至于标题写的是 "task family" 还是 "任务族" 还是 "project context"，不应影响路径选择。
当前实现中，用户把 "task family" 写成 "task description"，structural 路径立即失效，整个文档退化为 generic 自由文本处理,即便文档本身具有完整的结构信息。
3.2 问题二：规范化逻辑过度依赖规则
由于结构化定义过于狭窄，"结构 → CanonicalCompileInput" 的映射只能使用规则代码（elif 链 + 别名表）实现。这与 Pipeline 的核心理念相悖：
Pipeline 的设计原则是：LLM 负责语义判断，确定性代码负责结构性校验。Stage 1–99 的 LLM 阶段正是基于这一原则设计的。
然而 adapter 层将本应是语义判断的工作（"这个 section 对应 inputs 还是 policies？"）用硬编码规则实现，导致：
扩展性差：新增任何语义类型都需要修改 Python 代码
脆弱性高：轻微偏离模板即完全失效
与下游 stages 的设计哲学不一致
3.3 问题三：False Binary——虚假的二分法
当前设计制造了一个非此即彼的路由结构：
输入情况
路由结果
问题
完全匹配模板
structural（规则解析）
精确但脆弱
任意偏差
generic（LLM 提取）
有信息但丢失结构优势
一个把 "task family" 写成 "task description" 的用户，其文档本身具有完整结构，却完全无法利用 structural 路径带来的信息增益。这导致了一个悖论：格式完全自由的文档反而比"稍有偏离的"结构化文档得到更好的处理。
4. 影响分析
4.1 用户侧
用户必须了解并使用一套特定的标题词汇才能激活结构化解析路径。这既没有在任何文档中明确告知，也缺乏容错机制。用户感知到的系统是"有时工作、有时不工作"，而原因完全不可见。
4.2 维护侧
硬编码映射表和别名表是维护负担。每次支持新的文档格式或语言都需要修改源码，且每次修改都需要人工回归测试 elif 链的完整性。
4.3 架构侧
Adapter 层的规则化处理与下游 stages 的 LLM 驱动设计形成风格割裂。它也是系统中少数无法通过 prompt 调整来改善行为的模块之一。
5. 建议方向
以下是供讨论的设计方向，非最终方案：
方向 A：扩展结构化检测的定义
将 detect() 从"标题词汇匹配"改为"文档形态判断"：检测 Markdown heading、key-value pairs、列表结构等形态特征。任何具有明确形态结构的文档均进入 structural 路径。
方向 B：LLM 驱动的语义映射
进入 structural 路径后，将"这个 section 对应什么语义角色"的判断交给 LLM，而非 elif 链。确定性代码保留用于后置校验（EvidenceRef 完整性、命名唯一性等）。
方向 C：结构信息与语义解耦
将 CanonicalCompileInput 的 raw_sections 和 hard_facts 解耦：structural 路径负责提取 sections（确定性），LLM 负责从 sections 推导出 facts（语义），验证器负责检查 facts 的合法性（确定性）。
这三个方向不互斥，可以组合实施。
6. 附注
本报告不涉及其他已识别的次要问题（如 llm_client: object 类型逃逸、feature flag 命名不对称等），那些问题可在本问题解决后一并处理。
